\section{Abstract}
Anker is a multi-persona \textbf{venture operating system}: a single web
application that a startup \textbf{founder} uses to raise a round, a
\textbf{venture / fund general partner (GP)} uses to source deals and run the back
office, and a \textbf{limited partner (LP)} uses to monitor their capital --- each
persona seeing a surface scoped to their role but drawing on one shared data and
intelligence layer.

Unlike a marketing site with a login, Anker embeds \textbf{institutional-grade
financial machinery} directly in the product: an option-pricing-model (OPM) 409A
valuation engine, a private-credit loan-servicing engine with covenant tracking,
an equity share-plan engine with cliff-aware vesting, and a fund-administration
layer that computes the standard private-capital performance metrics (TVPI, DPI,
RVPI, MOIC, and money-weighted IRR) from a live ledger. Around this sits an
\textbf{AI layer} --- a provider-agnostic model router feeding a tool-calling
agent that adapts into three distinct \emph{persona copilots} --- and a
\textbf{semantic matching} subsystem over a database of \textbf{47{,}275}
investors and decision-makers.

This paper documents the system end-to-end: the architecture, the exact
mathematics behind each engine (with derivations), the machine-learning and
quantitative methods, the user workflows, and the security posture. It closes
with an honest empirical section grounded in the real production dataset.

\section{Introduction \& Market Position}
\subsection{The problem}
The venture lifecycle is served by a patchwork of point tools: one product for the
cap table, another for the data room, a CRM for investor relationships, a
spreadsheet for the fund model, a separate portal for LP reporting, and nothing
that connects the founder raising capital to the investor deploying it. The data
that matters is fragmented across these tools and across the boundary between the
two sides of the table.

Anker's thesis is that \textbf{the founder side and the fund side are the same
graph} --- companies, investors, rounds, positions, and people --- and that a
single system holding that graph can (a) remove the integration tax, and (b) apply
intelligence across the whole lifecycle rather than within a single silo.

\section{System Architecture}
\subsection{Stack}
Anker is a server-first \textbf{Next.js (App Router)} application in
\textbf{TypeScript}, styled with \textbf{Tailwind CSS v4}, deployed on
\textbf{Vercel}, backed by \textbf{Neon} (serverless Postgres), with
authentication delegated to \textbf{Supabase Auth}. The package manager is
\textbf{pnpm}. The AI layer routes across multiple LLM back-ends.

\subsection{The pure-math / service split}
A deliberate decision underpins every financial engine: the \textbf{mathematics is
isolated in pure, dependency-free modules} (\texttt{lib/modules/*}) that import no
database driver. This yields three properties: (1) \emph{testability} --- every
formula is exercised against textbook expected outputs; (2) \emph{isomorphic
execution} --- the identical function runs on the server (authoritative
computation) and in the browser (live ``as-you-type'' projections), guaranteeing
the number shown equals the number stored; (3) \emph{auditability} --- because the
math never touches I/O, a reviewer can verify a valuation from a single file.

\subsection{The derived-value discipline}
\textbf{Quantities that can be computed are never hand-typed.} A loan's outstanding
balance is $\text{principal}-\sum \text{principal\_portion}$ over the payment
ledger; a grant's exercised total is $\sum \text{quantity}$ over the exercise
ledger; a fund's called capital is the sum of capital-call line items. Each is
recomputed from its ledger after every mutation, eliminating an entire class of
reconciliation bugs endemic to spreadsheet-based management.

\section{Identity, Personas \& Access Control}
Every destination is tagged with the personas that may see it:
\texttt{personas: ["founder"|"vc"|"lp"]}. A user resolves to an active persona via
workspace membership; a user with no membership, or a \textbf{platform owner},
resolves to \texttt{null} (``sees everything''). Two \emph{platform tiers} sit
above per-workspace roles: \textbf{owner} (full oversight, firewalled from tenant
private records) and \textbf{admin} (staff), with $\text{owner}\supset\text{admin}$.
Route protection is centralized in a server guard that fails safe and always lets
owners through. Registration is \textbf{invite-only and fails closed}: without a
configured \texttt{SIGNUP\_INVITE\_CODE} secret, nobody can register. Login returns
a deliberately generic ``Invalid email or password'' (no user enumeration) and
redirects only to internal paths (open-redirect guard; see \S12).

\section{The Tier-1 Financial Engines}
Each ships as a pure-math module verified against textbook results, a server
service that persists and scopes, a REST surface, and a detail UI that projects
live.

\subsection{The 409A / Option-Pricing-Model Valuation Engine}
A 409A valuation sets the fair market value (FMV) of \emph{common} stock --- the
basis for option strike prices --- typically below the preferred price, because
common lacks the preferences of preferred. Anker uses the \textbf{Option Pricing
Model (OPM)} back-solve, treating each class of equity as a \textbf{call option} on
total equity value.

\subsubsection{Black--Scholes as the primitive}
The OPM prices equity claims as European calls on total equity value $S$ struck at
each \emph{breakpoint}:
\begin{equation}
C(S,K,\sigma,r,T) = S\,\Phi(d_1) - K e^{-rT}\,\Phi(d_2),
\end{equation}
\begin{equation}
d_1 = \frac{\ln(S/K) + (r + \tfrac{1}{2}\sigma^2)T}{\sigma\sqrt{T}},
\qquad d_2 = d_1 - \sigma\sqrt{T},
\end{equation}
where $S$ is total equity value, $K$ a breakpoint, $\sigma$ equity volatility, $r$
the risk-free rate, $T$ years to liquidity, and $\Phi$ the standard-normal CDF,
implemented with the \textbf{Abramowitz--Stegun} rational approximation (max abs
error $\approx 7.5\times10^{-8}$). Boundary tests: $C(S,0)=S$ and $C(0,K)=0$.

\subsubsection{Two-class waterfall \& breakpoints}
With one preferred series (liquidation preference $LP$, fully-diluted ownership
fraction $p$) and common, total value $W$ is allocated across breakpoints:
$[0,LP)$ preferred only; $[LP,CP)$ common only; $[CP,\infty)$ pro-rata, where the
\emph{conversion point} is $CP = LP/p$. Each interval's value to a class is a
\emph{call spread} (a difference of Black--Scholes calls). The common allocation:
\begin{equation}
V_{\text{common}}(W) = \big[\,C(W,LP) - C(W,CP)\,\big] + (1-p)\,C(W,CP).
\end{equation}

\subsubsection{The back-solve}
The observed preferred price implies total equity value. Anker solves for the $W$
such that OPM-allocated preferred value equals $\text{prefShares}\times
\text{recentPrice}$,
\begin{equation}
\text{find } W \ \text{s.t.}\ V_{\text{preferred}}(W) = \text{prefShares}\times
\text{recentPrice},
\end{equation}
by \textbf{bisection} (robust; monotone objective; derivative-free). The per-share
common FMV is $V_{\text{common}}(W^\ast)/\text{commonShares}$, optionally reduced
by a discount for lack of marketability (DLOM).

\subsubsection{Worked verification}
For \textbf{8{,}000{,}000} common and \textbf{2{,}000{,}000} preferred at a recent
preferred price of \textbf{\$1.00} ($\sigma=0.6$, $r=0.04$, $T=4$, DLOM off), the
back-solve recovers a total equity value at which preferred is worth exactly
\textbf{\$2{,}000{,}000}, and common FMV solves to $\approx$ \textbf{\$0.4441} ---
i.e.\ common is marked at $\approx$ 44\% of the preferred price. This is the
module's canonical regression test.

\note{\textbf{Caveat (from the product's own methodology writeup):} the two-class
OPM is appropriate for a single non-participating preferred series. Multi-series
stacks, participating preferred, and safe-harbor reliance require a fuller
waterfall and an independent appraisal.}

\subsection{The Loan-Servicing (Private-Credit) Engine}
\subsubsection{Amortization}
For a fully-amortizing loan, the \textbf{level payment} $A$ on principal $P$,
periodic rate $i=\text{APR}/f$, over $n$ periods, is the annuity formula
\begin{equation}
A = P\cdot\frac{i\,(1+i)^n}{(1+i)^n - 1}.
\end{equation}
Each period splits into $\text{interest}_t = i\cdot\text{balance}_{t-1}$ and
$\text{principal}_t = A - \text{interest}_t$, with
$\text{balance}_t = \text{balance}_{t-1} - \text{principal}_t$. Interest-only,
bullet, and revolving structures are also supported.
\emph{Verification:} \$100{,}000 at 12\% APR over 12 monthly periods yields a level
payment of \textbf{\$8{,}884.88}.

\subsubsection{Accrual \& the interest-first ledger}
Between scheduled payments, interest accrues on an \textbf{Actual/365} basis:
\begin{equation}
\text{accrued} = \text{balance}\times\text{APR}\times\frac{\Delta_{\text{days}}}{365}.
\end{equation}
A recorded payment is applied \emph{interest-first}, the remainder to principal,
and the outstanding balance is recomputed from the ledger. Covenants (financial,
reporting, affirmative, negative) are tracked with status and tested-at date.

\subsection{The Share-Plans (Equity Vesting) Engine}
\subsubsection{Vesting mathematics}
For a grant of $N$ options, total vest $M$ months, cliff $c$ months, and $m$ whole
months of credited service:
\begin{equation}
\text{vested}(m) =
\begin{cases}
0, & m < c,\\[4pt]
\min\!\Big(N,\ \big\lfloor N\cdot \tfrac{\min(m,M)}{M}\big\rfloor\Big), & m \ge c.
\end{cases}
\end{equation}
Nothing vests before the cliff; at the cliff the elapsed fraction vests \emph{at
once} (12-of-48 $\Rightarrow$ 25\%); thereafter straight-line to 100\% at $M$.
Termination freezes credited service; exercisable $=\max(0,\ \text{vested}-
\text{exercised})$.
\emph{Verification:} 48{,}000 options, 48-month vest, 12-month cliff: 0 at month
11; \textbf{12{,}000} at month 12; \textbf{24{,}000} at month 24; capped at
\textbf{48{,}000} past month 48; termination at month 30 freezes at
\textbf{30{,}000}.

%==================== 7 ====================
\section{Fund OS --- Fund Administration \& Performance Mathematics}
\subsection{The performance metric suite}
\begin{equation}
\text{DPI} = \frac{\text{Distributions}}{\text{Paid-in}},\quad
\text{RVPI} = \frac{\text{NAV}}{\text{Paid-in}},\quad
\text{TVPI} = \text{DPI}+\text{RVPI} = \frac{\text{Distributions}+\text{NAV}}{\text{Paid-in}}.
\end{equation}
Gross MOIC on a position is $(\text{realized}+\text{unrealized})/\text{cost}$.

\subsection{Money-weighted return (IRR)}
The fund IRR is the rate $x$ solving the NPV identity over dated cash flows $CF_k$
at times $t_k$ (years),
\begin{equation}
\sum_k \frac{CF_k}{(1+x)^{t_k}} = 0,
\end{equation}
calls negative, distributions plus terminal NAV positive; solved numerically
(Newton--Raphson with a bisection fallback for irregular flows). NAV of record is
the sum of position fair values from the Valuations engine.

\subsection{Waterfall, pacing \& forecasting}
Carried-interest distributions follow the fund's waterfall (return of capital
$\to$ preferred return / hurdle $\to$ GP catch-up $\to$ carry split), modelled so
LP/GP splits reconcile to the ledger. Fund Forecasting projects deployment pacing,
reserve policy, and projected returns --- the portfolio-construction analogue of a
position-sizing strategy.

\subsection{The Fund OS module map}
Fund OS is not a single dashboard but a workspace of $\sim$24 dedicated modules,
each a route under \texttt{/dashboard/portfolio/fund/*}, all reconciling to the
same ledger:
\begin{itemize}[leftmargin=1.2em,itemsep=1pt]
\item \textbf{Capital \& cash flow} --- \texttt{calls} (capital calls, with a
per-call detail view, a table view, and a ``new call'' wizard),
\texttt{distributions} (waterfall-driven, per-distribution detail + table + new),
\texttt{ledger} (the append-only source of the derived NAV / paid-in / DPI).
\item \textbf{Investors \& economics} --- \texttt{partners} (GP/LP roster),
\texttt{lps/[lpId]/statement} (per-LP capital-account statement),
\texttt{lp-imports} (bulk onboarding), \texttt{economics} (management fee, carry,
hurdle), \texttt{syndication} (SPVs / co-invest).
\item \textbf{Portfolio \& deals} --- \texttt{deals} (pipeline, with a
\texttt{[dealId]} detail), \texttt{investments} (positions of record),
\texttt{explorer}, \texttt{performance} (TVPI/DPI/RVPI/IRR), \texttt{tear-sheet},
\texttt{assessment} (fund-strength framework, incl. an assessment \texttt{wheel}).
\item \textbf{Governance \& reporting} --- \texttt{documents},
\texttt{legal} (review, fields, per-document \texttt{[docKey]}), \texttt{reports},
\texttt{management}, \texttt{plan}, plus \texttt{fund-tax} and the standalone
\texttt{tools/vc-fund-model} and \texttt{tools/fund-of-funds} modellers.
\end{itemize}
Every dollar figure on every one of these pages is \emph{derived} from the ledger
(\S3.3), not hand-entered --- the single discipline that lets two-dozen views stay
mutually consistent.

The active persona is injected into the system prompt with the persona's real

\subsection{AI workflows --- current and expanding}
Beyond conversational Q\&A, the agent runs \emph{multi-step operational workflows}
end-to-end. The ones in production today:
\begin{itemize}[leftmargin=1.2em,itemsep=1pt]
\item \textbf{Founder discovery run} --- from a thesis or uploaded deck, embed
$\to$ retrieve $\to$ score $\to$ dedupe $\to$ emit a ranked, exportable investor

\item \textbf{Reply handling} --- inbound replies are parsed and classified
(\texttt{lib/ai/reply-handler.ts}) to advance the CRM stage and surface hot leads
in the shared inbox.
\end{itemize}
\emph{Expanding:} document/spreadsheet co-authoring, a Fund-Copilot IC-memo
generator over the deal record, and an Investor-Copilot capital-account explainer
that narrates calls and distributions in plain language --- each a thin agent layer
over data and engines that already exist, which is why they can ship incrementally.

\section{Quantitative \& Machine-Learning Methods}
This section documents the methods actually present. It deliberately does
\textbf{not} report market-trading backtests for a strategy the platform does not
run; the quantitative core is derivatives-style valuation, credit modelling,
portfolio construction, and semantic ranking.

\subsection{Semantic investor matching}
Discovery ranks \textbf{47{,}275} investors for a company/thesis via
\textbf{embedding-based semantic retrieval}. A company/thesis and each investor
profile are encoded to dense vectors $u,v\in\mathbb{R}^d$; fit is scored by
\textbf{cosine similarity}
\begin{equation}
\operatorname{sim}(u,v) = \frac{u\cdot v}{\lVert u\rVert\,\lVert v\rVert},
\end{equation}
computed in Postgres via pgvector's distance operator (HNSW-indexed), then combined
with hard filters (stage, geography, check size, sector, recent activity) and
\emph{warm-intro} signals from a shortest-path over the relationship graph, so the
final ranking blends \emph{fit} and \emph{reachability}.

\subsection{Thesis scoring \& enrichment}
A scoring tool grades firms against a thesis (bounded batches, $\le 40$ per call);
an enrichment tool fills thin records from public sources. Both are LLM-in-the-loop
with rate-limited failover, producing exportable spreadsheets rather than opaque
scores.

\subsection{Option-pricing math as the derivatives core}
The 409A engine (\S6.1) \emph{is} the platform's derivatives-pricing model: it
treats each equity class as a call option and prices call spreads across
breakpoints with Black--Scholes --- the same mathematics used to price options in
public markets, applied to private structures, and legally consequential (it sets
strike prices).

\subsection{On ``trading strategies''}
Anker is a venture operating system, not a trading system, and this paper will not
manufacture a strategy or backtest to fit a narrative. The honest mapping: option
pricing (\S6.1) is the derivatives math; credit servicing (\S6.2) the fixed-income
math; pacing/reserves (\S7.3) the portfolio-construction math; IRR/TVPI/DPI (\S7)
the performance math; semantic ranking (\S9.1) the ML. Any future market-facing
strategy would be documented here with the same rigour --- and never before it
exists.

\section{Core Workflows \& the Founder Campaign Engine}
\subsection{Founder: from ``Pitch us'' to investor inboxes}
The founder's headline workflow is model (Cap Table, 409A, Share Plans, Runway)
$\to$ Raise Pipeline (by stage) $\to$ Data Room (12-section diligence taxonomy,
watermarked / tokenized / expiring share links with view analytics) $\to$ Outreach.
The outreach step is not a mail-merge; it is an autonomous \textbf{campaign engine}
that turns a single ``Pitch us'' submission into a ready-to-send, personalized
investor campaign.

\subsubsection{The orchestrator pipeline}
One submission is driven through an idempotent, status-gated state machine
(\texttt{lib/campaign/orchestrator.ts}). Each stage flips the submission's status
so an overlapping cron tick can never double-process it:
\begin{equation*}
\small
\text{received}\xrightarrow{\text{claim}}\text{assessing}\longrightarrow
\begin{cases}
\text{declined} & \text{(gate fails}\to\text{feedback)}\\[2pt]
\text{campaign\_ready} & \text{(gate passes}\to\text{matched+drafted)}
\end{cases}
\end{equation*}
\begin{enumerate}[leftmargin=1.4em,itemsep=1pt]
\item \textbf{Ingest} --- pull deck + up to three data-room docs from Blob storage.
\item \textbf{Extract} --- OCR/vision + text to a structured \texttt{StartupProfile};
founder-typed form fields are treated as \emph{higher-trust} than extraction and
overlay it, so a deck that fails to parse still yields a usable profile.
\item \textbf{Readiness gate} --- a conservative LLM assessment scores the startup
against a five-dimension rubric; below the threshold (default \textbf{62/100}) the
submission is auto-declined \emph{with constructive feedback}, and the pipeline
stops. This is the ``100+ startups assessed'' capability (\S13.3) in operation.
\item \textbf{Match} --- \texttt{runFounderMatching} ranks the investor universe;
only contacts with an email and a match score $\ge$ the floor (default
\textbf{55}) survive, capped at \texttt{maxInvestors} (default \textbf{100}).
\item \textbf{Create campaign + mint tokens} --- an \texttt{outreach\_campaign} row
plus one \texttt{campaign\_crm\_entry} per investor; each entry gets a signed
\emph{interest token} backing one-click \emph{Interested} / \emph{Not-interested}
/ \emph{View} links.
\item \textbf{Draft} --- per-recipient subject + body generated in a
concurrency-limited batch (8-wide), each grounded in the startup profile and the
specific investor's match rationale.
\item \textbf{Hand off} --- status becomes \texttt{campaign\_ready}; the sender
takes over.
\end{enumerate}

\subsubsection{Wave-based sending}
A cron sender (\texttt{/api/cron/campaign-send}, \texttt{CRON\_SECRET}-gated,
fail-closed) ships the next \textbf{wave} of drafted-but-unsent emails per active
campaign (default wave \textbf{20}). Small waves protect domain reputation and let
early results be observed before the next wave goes. Each message carries the
founder story, a deck link, the one-click interest links, an Anker AI signature,
and a reply-to/BCC so replies land in the shared inbox; when a campaign's queue
drains, the submission flips to \texttt{completed} and the founder gets a wrap-up
email. Two admin toggles govern automation:
\begin{center}\small
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{Setting} & \textbf{Default} & \textbf{Effect}\\
\midrule
\texttt{readinessThreshold} & 62 & Below this, auto-decline with feedback\\
\texttt{scoreFloor} & 55 & Minimum match score to include an investor\\
\texttt{maxInvestors} & 100 & Cap on investors per campaign\\
\texttt{waveSize} & 20 & Emails per send wave\\
\texttt{autoAssess} & on & Cron auto-processes new submissions\\
\texttt{autoSend} & on & When off, a human releases each campaign\\
\bottomrule
\end{tabular}
\end{center}
Settings live in a single DB row read on every assessment/send, so an operator
retunes the engine from the console with no redeploy.

\subsubsection{Deliverability guardrails}
Because the investor list is \emph{organically sourced} rather than opt-in, list
hygiene is enforced before send by a dependency-free verifier
(\texttt{lib/outreach/email-quality.ts}) applying four ordered gates ---
(1)~format regex, (2)~role-address rejection (\texttt{info@}, \texttt{hello@},
\texttt{noreply@}, \ldots), (3)~a hard-bounce suppression list carried forward
from the prior batch, and (4)~a live DNS \texttt{MX} check (per-domain cached) ---
so a message only sends to an address that is well-formed, personal, not
previously bounced, and whose domain can actually receive mail. Post-send, a
poller (\texttt{lib/email/resend-sync.ts}) reconciles Resend's \texttt{last\_event}
back into per-message status and open/click counters for the inbox. The measured
effect of these guardrails is reported in \S13.4.

\subsection{VC / GP}
Deal Flow $\to$ IC $\to$ close into positions; LP Matchmaking; the full back office
(capital calls, distributions, SPVs / syndication, KYC/AML, fund tax, contracts,
compliance) across the $\sim$24 Fund OS modules (\S7.4); reporting and monitoring.
GPs also run their \emph{own} outreach (a dedicated LP campaign builder,
\texttt{/dashboard/outreach/lp-campaign}) over the same engine --- e.g.\ the
family-office webinar campaign in \S13.4.

\subsection{LP: the Investor Room}
LPs get a self-serve portal (\texttt{/lp}) --- a branded overview, a
\texttt{documents} vault, a \texttt{distributions} view, and \texttt{help} ---

with an explicit, badged owner-oversight mode (the one logged exception to the

\section{Security, Compliance \& Auditability}
\begin{itemize}[leftmargin=1.2em]
\item \textbf{Authentication} --- Supabase sessions; invite-only, fail-closed
registration; generic login errors.
\item \textbf{Open-redirect remediation} --- the post-login \texttt{?next=} target
was applied without validation, allowing \texttt{?next=https://evil.com} to
redirect a freshly-authenticated user off-site (CWE-601). Both the login page and
OAuth callback now accept internal paths only.
\item \textbf{Owner$\to$tenant firewall} --- owners see aggregate/existence data,
not tenant private records, enforced structurally; one explicit, logged LP-portal
oversight exception.
\item \textbf{Immutable audit log} --- an append-only \texttt{audit\_events} trail
(actor, action, target, metadata, IP, UA) with a filterable admin feed; writes are
best-effort so auditing never breaks the action it records.
\item \textbf{Compliance register} --- enumerates the regulatory obligations a U.S.
VC fund faces and flags what applies to the fund's profile.
\end{itemize}

\item \textbf{Zero spam complaints across 719 sends} --- the strongest single

\section{Appendix A --- Formula Reference}
\textbf{Black--Scholes call.} $C = S\Phi(d_1)-Ke^{-rT}\Phi(d_2)$,
$d_1=[\ln(S/K)+(r+\sigma^2/2)T]/(\sigma\sqrt{T})$, $d_2=d_1-\sigma\sqrt{T}$.\\
\textbf{OPM common allocation.} $V_{\text{common}}(W)=[C(W,LP)-C(W,CP)]+(1-p)C(W,CP)$,
$CP=LP/p$.\\
\textbf{409A back-solve.} find $W^\ast$ s.t.\ $V_{\text{pref}}(W^\ast)=
\text{prefShares}\cdot\text{recentPrice}$ (bisection);
$\text{commonFMV}=V_{\text{common}}(W^\ast)/\text{commonShares}\cdot(1-\text{DLOM})$.\\
\textbf{Level loan payment.} $A=P\,i(1+i)^n/[(1+i)^n-1]$, $i=\text{APR}/f$.\\
\textbf{Actual/365 accrual.} $\text{accrued}=\text{balance}\cdot\text{APR}\cdot
\Delta_{\text{days}}/365$.\\
\textbf{Vesting.} $\text{vested}(m)=0$ if $m<c$, else
$\min(N,\lfloor N\min(m,M)/M\rfloor)$; $\text{exercisable}=\max(0,\text{vested}-
\text{exercised})$.\\
\textbf{Fund metrics.} $\text{DPI}=D/PI$, $\text{RVPI}=\text{NAV}/PI$,
$\text{TVPI}=(D+\text{NAV})/PI$, $\text{MOIC}=(\text{real}+\text{unreal})/\text{cost}$.\\
\textbf{IRR.} solve $\sum_k CF_k/(1+x)^{t_k}=0$ (Newton--Raphson + bisection).\\
\textbf{Cosine similarity.} $\operatorname{sim}(u,v)=(u\cdot v)/(\lVert u\rVert
\lVert v\rVert)$.
